# Adversarial critique — "The Trip Is the Deadline" roadmap

Verified against the repo at `/Users/grohmannpatrik/Claude/Projects/Ázsia nomad trip planning/asia-nomad-planner` (git HEAD f14f824, 2026-06-30). Most codebase claims check out: `fetchActiveTrip` newest-row rule (`product/src/lib/trips/queries.ts:7-18`), `Math.random()` ids, `makeDefaultState()` seeding, `schema.sql:54-113` unused normalized tables, `can_access_trip` at `schema.sql:177`, `trips_update` open to all members (`schema.sql:212`, re-applied in migration 01), migration 03's `is_admin()`/`to authenticated` anti-scraping stance, `ARCHITECTURE.md:138` Phase-2 normalization promise, USGS/ringsData patching in `Globe.tsx:84-99`, and the static app's trip switcher in `js/cloud.js`. The three-regime data model is genuinely the right call. But the design contains one broken flagship mechanism, several verified factual errors, and a schedule that doesn't fit its own arithmetic.

## 1. Factual errors about the codebase / 2026 ecosystem

**1.1 — MAJOR. The stay-cancellation notifier's data does not exist.** The design claims "Data already in `state.stays` (charge/cancel dates)". False. `Stay` in `product/src/lib/trips/types.ts:26-39` has `ppn/nights/rating/status/notes` — no charge date, no free-cancel-until field. The owner's one real deadline lives only in a prose string (`defaultState.ts:26`: "Free cancel until Aug 29"). The "highest personal value, needs no external API" feature actually needs: schema addition to `Stay`, form fields in `StayForm.tsx`, and — for "push" — Web Push infra (service worker, subscription table, VAPID keys) that doesn't exist; there is no `manifest`/`sw.js` anywhere in `product/`. **Fix:** add `cancelUntil`/`chargeDate` to `Stay` in M0; ship the notifier as email-only (Resend) in M1; defer Web Push to the M1 PWA spike.

**1.2 — MAJOR. Frankfurter cannot price this trip.** Frankfurter serves ECB reference rates only. The app's own rate table (`defaultState.ts:14-18`) needs VND, KHR, TWD, NPR, LKR — none are ECB currencies. Vietnam and Cambodia are on the actual route. The "FX watcher: trivial, M0" row silently fails for the currencies that matter most. **Fix:** use open.er-api.com / exchangerate-api-style free sources (160+ currencies) for the cron; keep Frankfurter only as a cross-check.

**1.3 — MAJOR. "Reused unchanged" understates the multi-trip blast radius.** `tk` is a singleton key `['active-trip']` (`keys.ts`), hardcoded into `useTripMutation.ts:20,27-35`, `useLedgerMutation.ts`, `useTripScreen.ts:13`, `prefetch.ts:14`, `SettingsClient.tsx`, `map/page.tsx`, and `CreateTripEmptyState.tsx` — 8 files, not "one function." Worse: the proposed "profile column **or localStorage**" for selected-trip id breaks `prefetchTripScreen`, which runs server-side and cannot read localStorage — the SSR prefetch would silently hydrate the wrong trip. **Fix:** parameterize keys as `tk.trip(id)`, persist selection in a cookie (readable by the server prefetch) with a profile-column fallback; budget ~1 pw for this alone in M0.

**1.4 — MINOR (verified small errors).** (a) "Stays cards already link to platforms" — false in `product/`; `StaysTab.tsx` renders `x.platform` as plain text, no `href` anywhere; affiliate plumbing is still small but it's net-new UI. (b) The id fix list misses `LedgerTab.tsx:11`, which has the same `Math.random()` pattern. (c) "37 cities' worth" of landmarks — it's 46 (37 in migration 04 + 9 in 05). (d) "~690 lines" domain core — actual: 493 (trips lib) + 92 (catalogue lib). None change conclusions.

**1.5 — MINOR (unverifiable-from-repo pricing claims).** Mux "10 videos / 100k delivery min free", AeroDataBox "600 free units/mo", Foursquare "10k free calls" are stated as facts; Foursquare in particular restructured pricing repeatedly through 2024–25 (credit-based). **Fix:** mark these three rows "verify at build time" and name fallbacks (OSM/Overpass for venues; skip flight status).

## 2. The flagship feature has a broken mechanism — MAJOR (borderline BLOCKER for M2 as specced)

The follow page (§3b) subscribes anon users to **Postgres Changes on `trip_events`** while stating "RLS stays fully closed to `anon`". These two sentences contradict each other: Supabase Postgres Changes enforces RLS per subscriber — a socket authenticated as `anon` receives zero events from a table whose only SELECT policy is `can_access_trip()`. The proposed mitigation ("mint a short-lived signed channel name via RPC") works for **Broadcast** authorization, not for Postgres Changes — you cannot sign your way into WAL rows you can't SELECT. As written, the family feed never updates. **Fix (pick one, spec it in M2):** (a) simplest — poll `shared_feed(token)` every 30–60s and keep Realtime only for the Broadcast position channel; or (b) the "Broadcast from Database" pattern — a trigger on `trip_events` calls `realtime.broadcast_changes()` into `trip:{id}:feed`, with an RLS policy on `realtime.messages` validating the token→channel mapping. Also note anon Realtime connections still consume the 200-connection quota. The design's risk #6 ("realtime is a new domain, underestimation risk") is thus self-fulfilling — the spec itself contains the first underestimation.

**Related media hole (M3) — MAJOR.** `shared_feed` is a SQL RPC, but anon media delivery needs **signed Storage URLs**, which cannot be minted from SQL — signing requires the Storage API/service key. So the follow-page photo path requires the Edge Function/route-handler the design only mentions as an option ("if not done via RPC"). Cloudflare Images "remote transforms" additionally require proxying the domain through Cloudflare — a whole new vendor + DNS coupling for an app on Vercel. **Fix:** commit to a Vercel route handler with service-role that validates the token and returns short-lived signed transform URLs (Supabase Pro image transforms); drop Cloudflare from the plan.

## 3. Sequencing and effort

**3.1 — MAJOR. The schedule fails its own arithmetic.** "~12 working weeks of **part-time** capacity" vs M0–M2 = 8–10 **person-weeks** plus M3 "straddling departure." At 50% part-time, 12 calendar weeks ≈ 6 pw — the must-ship set doesn't fit even before the underestimates in 1.1/1.3/2 land. M0 alone bundles the owner's entire polish wishlist (7 screens), the multi-trip refactor, an onboarding wizard, theming + destination palettes, and the timezone fix into "3–4 pw." **Fix:** split M0 → M0a *structural* (multi-trip/cookie selection, empty-trip onboarding, `crypto.randomUUID()`, `Stay` cancellation fields) and M0b *polish*, and pre-declare the cut list: destination palettes, safety-feed crons (the globe already has client-side USGS + monsoon), flight status, and half the polish move behind M2/M3. The exit criteria are good; the buffers are zero.

**3.2 — MAJOR. No offline story for the one screen used on the road.** `/live` will be used on ferries, night buses, and rural SIMs. The product app has no offline layer at all (TanStack Query cache is in-memory; no persister, no service worker — the *static* app's localStorage cache was the fallback, and it's frozen). A check-in POST on a dead connection is simply lost. Append-only events are the *easy* case for an outbox — but it's unplanned work. **Fix:** scope an IndexedDB outbox (or `persistQueryClient` + persisted mutations) into M1, and make the M1 PWA test explicitly include airplane-mode check-in → later sync.

**3.3 — MAJOR (expectation-setting). "Live location" is not live on iOS.** A PWA cannot ping geolocation in the background; Safari suspends the page when locked. "1 ping / 5–10 min" happens only while the traveller keeps the app foregrounded. The family follow page will realistically show "last seen at check-in." The design flags "PWA jank" generically but not this hard platform limit — and it's the demo the whole option is sold on. **Fix:** design the position layer as event-driven ("last seen: Hoi An, 2h ago" from check-ins/app-opens), not a tracker; say so on the follow page. This also quietly answers attack (5): the mobile story *works* for check-ins, camera upload, and follow pages, but the owner's wish #1 (native apps from the same project) is deprioritized, not served — Next.js SSR doesn't wrap in Capacitor, and the design's own admission stands: a future native app is a full rewrite of the UI bucket. That trade should be surfaced to the owner as a decision, not buried in risk #2.

**3.4 — MINOR. Vercel Hobby cron limits.** Hobby allows ~2 cron jobs at once-per-day precision; the plan lists 4+ cron routes pre-trip while claiming paid infra starts only at M3. **Fix:** one daily dispatcher route fanning out internally, or Supabase pg_cron (free) from day one.

**3.5 — MINOR. Seeded `places` have no coordinates.** Landmarks in migration 04 carry `name/why/when/how/cost/time` — no lat/lng (verified in the jsonb). "One-tap check-in, nearby places by distance" degrades to every landmark sitting on the city centroid, and restaurants don't exist until M4 Foursquare. **Fix:** geocode landmarks in migration 07 (Wikidata/Nominatim batch, ~46 cities is an afternoon) and design `/live` check-in as city-scoped list + "add place here" (GPS from the phone) rather than distance-sorted.

## 4. Security / RLS holes

**4.1 — MAJOR. Column-level exposure when the catalogue opens to anon (M4).** Risk #4 says "keep premium fields behind auth," but RLS is row-level: `cities_select to anon using (true)` exposes the entire `attributes` jsonb — landmarks, costs, weather, everything — in one scrape. **Fix:** expose a `public_cities` view (or separate table) with the SEO subset; never flip the base-table policy.

**4.2 — MINOR-MAJOR. Ownership takeover via `trips_update`.** The current policy (`schema.sql:210-212`, no `WITH CHECK`) lets any member UPDATE any column — including `owner`. A member can reassign ownership to themselves and still pass the check (they remain a member). Harmless between a couple; not harmless once viewer invites and share tokens multiply. **Fix in migration 06:** editor-only update + trigger/column-revoke freezing `owner`; extend the same editor-gating to `trip_events`/`check_ins`/`media` INSERTs (the drafted `can_access_trip` for-all-ops policy lets a *viewer* post to the couple's feed).

**4.3 — MINOR. SECURITY DEFINER hygiene.** Existing `can_access_trip`/`has_pending_invite` lack `set search_path = public` (migration 03's `is_admin` has it). The new anon-facing RPCs (`shared_trip_summary` etc.) must pin `search_path`, be `EXECUTE`-granted to `anon` only (revoke from `public`), and get a default token expiry — the design lists expiry as an optional mitigation; make it a default. One more spec gap: the follow page's globe needs city coordinates, but the catalogue is authenticated-only until M4 — `shared_trip_summary` must therefore return route lat/lngs itself (definer join), and `Globe.tsx` needs a props-only wrapper decoupled from `useTripScreen`.

**4.4 — MINOR (bonus, argues for the design's own M0 item).** `makeDefaultState()` seeds every new trip with the owner's **real** booking confirmation number and flight details (`defaultState.ts:26,31,36`). The empty-onboarding replacement isn't just UX — it's a privacy leak the moment a third user signs up. Do it first in M0.

## What's genuinely right

The three-regime split (LWW jsonb plan / append-only relational live / cached world) is the strongest idea here and dissolves the false "migrate the blob" debate; rescinding `ARCHITECTURE.md` Phase 2 is correct. Risk #1 (LWW forever) and #7 (community may be nobody) are honestly stated. The integration triage table is mostly sober — visa "curate don't integrate" and the PSD2 "defer hard" call are exactly right. The affiliate-before-Stripe business sequencing is sound.

**VERDICT: SOUND-WITH-FIXES**

The three fixes that matter most:
1. **Respecify the follow feed's realtime mechanism (M2):** RPC polling or trigger-driven `realtime.broadcast_changes()` — Postgres Changes to anon subscribers cannot work with RLS closed, and this is the flagship demo.
2. **Re-cut the pre-trip schedule:** split M0, pre-commit the cut list (palettes, safety crons, flight status), add `Stay.cancelUntil`/`chargeDate` + email-only notifier, and add the offline outbox for `/live` — the current plan exceeds its own stated capacity before any overrun.
3. **Harden the sharing/multi-trip foundations in migration 06:** cookie-based selected-trip + parameterized query keys (8 files, server prefetch included), editor-only writes with `owner` frozen, pinned `search_path` + expiring tokens on the anon RPCs, and a `public_cities` view for M4 instead of flipping base-table RLS.
